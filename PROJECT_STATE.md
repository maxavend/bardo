### 0.2 — Calidad

Completed.

Demonstrated capabilities:

- A native `BardoTests` XCTest target is generated by XcodeGen.
- The `Bardo` scheme builds the app and runs the test target.
- GitHub Actions validates pull requests and pushes to `main` on a macOS 15 runner using Xcode 16.4.
- CI installs XcodeGen, regenerates the project, builds Bardo, verifies the application bundle, and runs the unit test suite.
- The workflow uses read-only repository contents permission.
- App lifecycle logging uses Apple's `OSLog.Logger` directly with a fixed Bardo subsystem and no custom logging framework.

SwiftLint was deliberately not introduced. At the current project size it would add a dependency and policy surface without catching a material class of defect that the compiler/tests do not already expose. This can be reconsidered when the codebase has enough production code to justify a lint policy.

No logging abstraction was introduced. Foundation uses `OSLog.Logger` directly for the single bootstrap lifecycle event, avoiding both sensitive content and an unnecessary wrapper API.

### 0.3 — Contratos del dominio

Completed.

Defined Foundation contracts:

- `AudioSource`
- `ProcessingState`
- `Recording`
- `Speaker`
- `TranscriptSegment`
- `Transcript`

The models are value types with explicit `Codable`, `Equatable`, and `Sendable` semantics where appropriate. `Recording` supports multiple audio sources so a future system-audio-plus-microphone recording can be represented without creating a special-case source type.

Round-trip tests demonstrate that recording and transcript values survive JSON encoding/decoding without losing identity, timing, speaker association, source information, or processing state.

Service protocols for capture, persistence, transcription, and diarization are intentionally **not** defined yet. Their real inputs/outputs do not exist in the domain at this phase, so defining them now would be speculative architecture. Each port will be introduced with its first concrete consumer.

## Architectural decisions

- Keep the application native: SwiftUI + Apple platform frameworks.
- Use XcodeGen as declarative project configuration; never treat the generated `.xcodeproj` as source.
- Use XCTest without an additional testing or mocking framework at Foundation scale.
- Keep CI pinned to the macOS 15 runner and Xcode 16.4 for deterministic Foundation validation.
- Use `OSLog.Logger` directly until a real need for shared logging behavior exists.
- Avoid a linter until there is enough code to justify a repository-wide style policy.
- Model domain data now; defer service-port abstractions until their first real use case.
- No third-party runtime dependency is allowed into Foundation without a demonstrated requirement.

## Data and migrations

No persisted application data exists yet, so there are no migrations.

The Phase 0 domain types are `Codable`, but this does not yet constitute a persisted on-disk schema. Persistence/versioning becomes a concern when Phase 1 introduces storage.

- CI intentionally uses Xcode 16.4; when GitHub removes that toolchain from its macOS 15 runner image, the workflow will need an explicit toolchain update rather than silently floating to a new Xcode major version.
- Domain contracts are intentionally small. New requirements should extend them only when demanded by a concrete phase, not preemptively.
